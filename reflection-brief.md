## Part 1 — Per-system

### System 1 — Agentic loop

1. **Loop control.** Quote the `stop_reason` sequence from one trace. Name the file and function that decides continue-vs-stop, and how.
   → Looking at the trace for claim_01_kitchen_fire in run 20260901_192722, the stop_reason sequence is as follows: turn 1 tool_use, turn 2 tool_use, turn 3 tool_use, turn 4 end_turn. The file that decides continue-vs-stop is claims_intake/loop.py, specifically the run() function. After every API call, the function checks response.stop_reason in a while True loop with no integer cap. If it sees end_turn, it immediately returns a FinalState object. If it sees tool_use, it executes every tool block, appends the results to the message list, and continues. Any other value raises UnexpectedStopReason. The loop is purely reactive to what the model signals, which means that nothing in the application code decides when to stop independently of the model.

2. **Anti-pattern.** Name one anti-pattern `test_antipatterns.py` checks for. What would break in your run if the loop used it?
   → The test_antipatterns.py suite checks that the loop never uses string-membership tests on the assistant's text content to make control flow decisions. For example, checking whether the word "completed" appears in a response before deciding to stop. If that anti-pattern were used in run 20260901_192722, claim_06_low_confidence_escalation would be the most likely result. That claim took 5 turns and the model's intermediate responses contained summary-like language before it ultimately decided to call in escalate_claim. A substring check on that language would either trigger a false alarm early exit before the escalation tool was called, or fail to recognize the stop condition at all and loop until the budget raised BudgetExceeded.

3. **Tool design.** Pick two tools with overlapping inputs. How do the descriptions prevent misrouting? What did a structured tool error let the agent do that a generic string would not?
   → Two tools with overlapping inputs are route_to_adjuster and escalate_claim. Both receive a completed claim picture after classification. Their descriptions separate them by confidence. For example, route_to_adjuster requires a resolved claim_type and severity, meaning the model is confident enough to send the claim forward. Meanwhile escalate_claim is explicitly described as the action to take when ambiguity cannot be resolved. In run 20260901_192722, claim_06 reached confidence 0.55 and the model correctly called escalate_claim with reason unresolved_ambiguity_on_root_cause rather than routing it. Structured tool errors also mattered here. In this instance when a tool handler returns a JSON object with is_error set to true, the agent can distinguish a transient failure (and retry) from a domain-level graceful error (as well as ask a clarifying/follow-up question), which a generic error string would not carry.

### System 3 — Claude Code config

8. **Path-scoped rules.** Quote the glob frontmatter from one rule file. Why is it better than a directory-level CLAUDE.md for cross-cutting conventions?
   → From .claude/rules/tests.md, the glob frontmatter reads paths: "/*.test.tsx" and "/*.test.ts". This is better than a directory-level CLAUDE.md for cross-cutting conventions because test files are co-located alongside source files throughout the entire tree. Objectively, Foo.tsx lives next to its Foo.test.tsx in src/components/, and a handler lives next to its test in src/api/. The validator confirmed this structure is correct especially, where the ecommerce-team-config . returned OK with exit code 0 when subsequently executed.

### System 4 — Orchestration

11. **Push work down.** Defects the SQL query returned vs warm-tier total. Name the indexed query. Why does the model never see the full history?
    → The warm tier holds 40 total records, confirmed by running w.count() after seeding in Output 04. When the shift ran with "--since 2026-04-25T00:00:00Z", the query returned exactly 3 defects. The indexed query is warm.defects_since(since_ts, limit=50) in shift_monitor/warm.py. This is backed by a SQLite index on the timestamp column, while the test test_defects_since_uses_index_and_does_not_load_full_table in the 33-test suite confirms this. The model never sees the full 40-record history because pipeline.py's gather_new_defects() performs the SQL filter before constructing the prompt, and build_rich_prompt() receives only the 3 new defects. Filtering at the database layer rather than in Python after loading the full table is what keeps the prompt small regardless of how large the warm tier grows.

12. **Crash recovery.** The resume-vs-fresh decision and its staleness threshold (`recovery.py`). Why is a fresh start with an injected summary sometimes more reliable than resuming?
    → The staleness threshold is 30 minutes, confirmed by the test test_threshold_constant_is_30_minutes in the 33-test suite. The recovery decision works as follows: if the scratchpad manifest shows a prior incomplete run and that run is less than 30 minutes old, the system resumes by injecting the prior scratchpad steps into the new prompt. If the prior run was already complete, or if more than 30 minutes have passed, the system starts fresh and injects only a summary of prior findings. A fresh start is sometimes more reliable than resuming because after 30 minutes, new defects may have arrived in the warm tier, and the model's prior intermediate reasoning was written for a different defect set. A clean summarized injection is more coherent and less likely to cause the model to reason from stale context than replaying a large partial scratchpad. A forked investigation stays isolated from the main state by writing to its own scratchpad path under a distinct hypothesis_id, meaning its entries never appear in the main shift_scratchpad.jsonl stream. The only way findings cross back is through merge_findings(), which appends selectively to the main scratchpad without rewriting or messing with the base state.

13. **Small state.** Byte size of your `hot_state.json`. Why does the budget matter for a system run once per shift, indefinitely?
    → Objectively, data/hot_state.json is 699 bytes, confirmed via ls -la in Output 04. The byte budget matters because hot_state.json is loaded into every shift's prompt. If it were to grow uncontrollably over months of shifts, each prompt would grow, eventually hitting the model's context limit and inflating per-shift token costs linearly. The solution is pipeline.py's _trim_to_budget() which enforces the ceiling by evicting the oldest active_alerts entries first. Separately, the test test_hotstate_rejects_more_than_20_hashes guarantees in code that the hash list cannot silently exceed 20 entries. A system run indefinitely must have bounded state or it fails silently.

14. **Three layers.** Point to a file/artifact for each layer and justify.

15. **Deterministic vs prompt.** Cite one behavior guaranteed in code (terminal tool, read-only allowlist, atomic write, byte budget) and one guided by prompt. When is each right?
    → A behavior guaranteed in code is the allowed-tools allowlist in deploy-check/SKILL.md where the harness enforces it structurally, and the skill literally cannot call Edit or Write regardless of what the model attempts. Similarly, _trim_to_budget() in pipeline.py enforces the hot_state byte ceiling in Python, and the 699-byte result in data/hot_state.json reflects that ceiling. These are right when the constraint is an absolute correctness or security boundary and no amount of good reasoning should be able to override it. A behavior guided by prompt is the escalation decision in System 1 claims_intake/system_prompt.py where it guides the model to call escalate_claim when confidence is unresolvably low. This is seen in run 20260901_192722, where claim_06 reached confidence 0.55 and escalated based on that guidance, not a hardcoded threshold. Prompt guidance is right when the behavior requires judgment about context and nuance that no finite rule set can enumerate.

16. **Context, two faces.** Compare context management in System 2 (intra-session) and System 4 (cross-session) with cited numbers from both. Same principle, different mechanism — how?
    → System 2 manages context within a single conversation where a 38,708-token transcript is assembled down to 16,844 tokens including a 56.48% reduction per budget.json which is done by compressing resolved threads to 421 and 448 tokens respectively as well as preserving the active thread verbatim at 15,789 tokens. This happens once, immediately before the model call, and produces a context tailored to that specific conversation. System 4 manages context across sessions where hot_state.json carries only 699 bytes of distilled state between shifts, and SQL pre-filtering delivers 3 defects from a 40-record warm tier so the per-shift prompt stays small regardless of total history. Both systems apply the same principle which gives the model only what it needs right now, but System 2 achieves this by compressing within a conversation while System 4 achieves it by never accumulating conversational state at all, distilling each session's output to a tiny structured artifact before the session ends.

17. **Reliability you can't see in one run.** Name one behavior a test guarantees that a single successful run would not reveal. Why does it matter before shipping?
    → The test test_hotstate_rejects_more_than_20_hashes in System 4's 33-test suite guarantees that inserting a 21st hash raises an error rather than silently growing the state file. A single successful shift run produces a hot_state.json with only 3 hashes and 699 bytes, which looks completely healthy. Without this test, there would be no way to know whether the 50th shift or the 500th shift would silently inflate the state until the prompt overflowed. The test reveals the behavior of the system at its boundary, not just on a normal path, and that boundary is exactly the one that fails in production after months of operation rather than in a demo. This is what automated tests guarantee that manual inspection of a single run structurally cannot.

18. **Blast radius.** Pick one system. What's the blast radius if it misbehaves, and what's the kill switch? Ground it in that system's tools, enforcement points, and state.
    → Taking System 4 as the example in this instance, if run_shift() in pipeline.py receives a malformed model response with no JSON fence, _parse_hot_state_update() returns None and the code falls back to preserving the prior hot_state values rather than corrupting state. As a result, the system degrades gracefully rather than crashing or writing incorrect outputs. The warm tier is never written to during a shift run since only defects_since() is called, so a bad run cannot corrupt the defect history. The scratchpad is append-only, meaning the worst outcome of a misbehaving run is one erroneous entry in shift_scratchpad.jsonl. This does not overwrite prior conclusions either. The kill switch is in essence is the "--recorded-response flag" where any shift can be replayed with a saved fixture (as demonstrated in Output 04 using fixtures/recorded_responses/shift_C_2026-04-30.json) to diagnose a misbehaving run without issuing a real API call or touching production state.

20. **What you'd change.** One architectural decision you'd make differently, grounded in what you observed.
    → System 2's compression policy is binary meaning resolved means summarize, active means preserve. The observed numbers make this concrete which included resolved_refund at 421 tokens and resolved_subscription at 448 tokens versus the active section at 15,789 tokens, meaning the active section is 93.7% of the assembled context. In a real copilot handling many resolved issues over a long session, a smarter policy would rank resolved conversations by recent and topical relevance to the active issue, allocating more summary tokens to a recently-closed thread that directly relates to the current problem as well as fewer to unrelated older threads. The current design is correct and simple for the two-issue scenario in the fixture, but it treats all resolved history as equally irrelevant to the active issue, which would not hold in a messier real-world conversation.
